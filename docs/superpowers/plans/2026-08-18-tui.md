# TUI Phase 1 — Implementation Plan

**Spec:** `docs/superpowers/specs/2026-08-18-tui-design.md` — read it first; this
plan argues from it and does not restate the design.

**Goal:** Replace bare `openair`'s scan-and-pair-everything with an interactive
device picker, and give streaming runs a live read-only dashboard. `--no-tui`
keeps today's behaviour.

**Architecture:** `crates/tui` (new lib) renders on the main thread while the
existing blocking stream runs on a worker. Numbers cross the boundary through a
shared `Arc<StreamStats>`; log lines cross through a `tracing` Layer backed by a
bounded ring buffer.

**Tech stack:** ratatui + crossterm (already workspace deps), `tracing`,
`serde_json` (already used by `pairings.json`).

## Global constraints

- No `Co-Authored-By` or Claude attribution in commit messages.
- Many small focused commits — one logical change each, committed as soon as it
  builds and tests pass. Do not batch to the end.
- `cargo clippy -- -D warnings` must stay clean; `cargo test` must stay green.
- Work in `C:\Users\antoi\OpenAir` (not the worktree).
- `crates/tui` must not depend on `openair-capture`.
- Commits are GPG-signed and need the user present for pinentry. If signing
  times out, stop and say so — never `--no-gpg-sign` or `--no-verify`.

## Task 3 — Settings persistence

**Files:** create `crates/tui/src/settings.rs`

**Produces:**
```rust
pub struct Settings {
    pub handoff: bool,
    pub latency_ms: u64,
    pub volume_db: f32,
    pub metadata: bool,
    pub graph: GraphKind,   // Buffer | Bandwidth
}
impl Settings {
    pub fn load() -> Self;              // never fails; defaults on any problem
    pub fn load_from(path: &Path) -> Self;
    pub fn save(&self) -> std::io::Result<()>;
    pub fn save_to(&self, path: &Path) -> std::io::Result<()>;
}
pub fn config_path() -> PathBuf;        // %APPDATA%\OpenAir\settings.json
```

Split `load`/`load_from` (and `save`/`save_to`) so tests use temp paths — the
same pattern used for the PTP clock identity file, which was untestable until
it was split this way.

Reuse whatever `pairings.json` already does to locate `%APPDATA%\OpenAir`
rather than re-deriving it.

**Tests (write first):** round-trip; missing file → defaults; corrupt JSON →
defaults, no panic; `version` newer than known → defaults; a `merge_flags` unit
covering flag > file > default precedence.

**Commit:** `feat(tui): persisted global settings`

## Task 4 — Log ring buffer + tracing layer

**Files:** create `crates/tui/src/logs.rs`

**Produces:**
```rust
pub struct LogLine { pub ts: String, pub level: Level, pub msg: String }
#[derive(Clone)]
pub struct LogBuffer(Arc<Mutex<VecDeque<LogLine>>>);
impl LogBuffer {
    pub fn new(capacity: usize) -> Self;
    pub fn tail(&self, n: usize) -> Vec<LogLine>;
}
pub fn layer(buf: LogBuffer) -> impl tracing_subscriber::Layer<S>;
```

Capacity 500, oldest dropped. The layer formats the event's message and fields
into `msg` — a `Visit` impl, same shape as `tracing_subscriber`'s own.

**Tests (write first):** capacity enforced and oldest dropped; `tail` returns
newest-last; a captured event's level and message text land in the buffer.

**Commit:** `feat(tui): bounded log buffer and tracing layer`

## Task 5 — Terminal setup and restore guard

**Files:** create `crates/tui/src/term.rs`

**Produces:**

pub struct TermGuard { /* restores on Drop */ }

`install_panic_hook` wraps the existing hook: leave raw mode and the alternate

worth the machinery.

## Task 6 — Picker state and input (no rendering)

**Files:** create `crates/tui/src/picker.rs`

**Produces:**
```rust
pub struct PickerState { /* devices, cursor, selection, settings */ }
impl PickerState {
    pub fn new(settings: Settings, paired: &[String], handoff_available: bool) -> Self;
    pub fn insert(&mut self, dev: AirPlayDevice);   // idempotent; keeps sort
    pub fn on_key(&mut self, key: KeyCode) -> PickerAction;
    pub fn rows(&self) -> Vec<PickerRow>;
}
pub enum PickerAction { None, Quit, Start, Hint(String) }
```

Sort: paired first, then name. `insert` must be idempotent — mDNS re-announces,
and a device appearing twice in the list would be the most visible possible bug.
`needs_pairing` is derived from `status_flags` (PIN required) with no local
pairing record.

Keys per spec: `↑`/`↓`, `space`, `h`, `+`/`-` (50 ms steps, clamped), `Enter`,
`q`/`Esc`. Enter with nothing selected → `Hint`. Enter on a `needs_pairing`
device → `Hint` naming the `openair pair "<name>"` command.

**Tests (write first):** sort order; `insert` idempotence on repeat announce;
selection toggle; latency clamp at both bounds; the two `Hint` paths.

**Commit:** `feat(tui): picker state machine`

## Task 7 — Picker rendering and CLI wiring

**Files:** `crates/tui/src/picker.rs` (render fn), `crates/tui/src/lib.rs`
(`run_picker`), `apps/cli/src/main.rs`

**Produces:** `pub fn run_picker(settings: Settings) -> io::Result<Option<PickerOutcome>>`
where `PickerOutcome { receivers: Vec<AirPlayDevice>, settings: Settings }`;
`None` means the user quit.

Inline viewport, ~12 rows. Event loop: poll crossterm with a short timeout,
drain `BrowseHandle::devices`, redraw. Save settings on exit.

CLI wiring:
- `--no-tui` flag via the existing `extract_flag`.
- Bare `openair` (and a streaming command naming no receiver) → picker; on
  `Start`, run the stream the CLI already builds.
- TUI off when `--no-tui` or `!is_interactive()`.
- The old scan-and-pair-everything path is what `--no-tui` bare `openair` runs.

**Tests:** a `util` test that `--no-tui` is extracted and removed from args.

**Manual check:** on a busy network, confirm the list fills incrementally and no
pairing traffic leaves the machine until Enter.

**Commit:** `feat(tui): interactive device picker` (+ a separate
`feat(cli): --no-tui and picker wiring` if the diff is large)

## Task 8 — `StreamStats` and stream-loop writes

**Files:** create `crates/client/src/stats.rs`; modify
`crates/client/src/lib.rs`

**Produces:** `StreamStats`, `ReceiverStat`, `ReceiverState` exactly as in the
spec, plus:
```rust
impl StreamStats {
    pub fn new(targets: &[GroupTarget]) -> Arc<Self>;
    /// Window minimum since the last call; rearms to i64::MAX.
    pub fn take_min_lead_ms(&self) -> Option<i64>;
}
```

Add an optional `stats: Option<Arc<StreamStats>>` parameter to
`stream_audio_buffered_multi` and write to it at points that already exist —
do not add new computation:
- `min_lead_ms` where `min_lead_ns` is already updated (the
  `play_deadline_ns(...) - ptp_now_ns()` line).
- `bytes_sent` where the AAC frame is queued.
- `latency_ms` where `current_latency` changes.
- `receivers` state in `reap_dead` and on reconnect success.
- `now_playing` in `send_metadata`.

Guard every write with `if let Some(s) = &stats` so `--no-tui` pays nothing.

**Tests (write first):** `take_min_lead_ms` returns the window minimum and
rearms; returns `None` before any sample.

**Commit:** `feat(client): StreamStats snapshot for observers`

## Task 9 — Dashboard derivation logic

**Files:** create `crates/tui/src/dashboard.rs`

**Produces:**
```rust
pub struct DashboardState { /* history rings, graph kind, log scroll */ }
impl DashboardState {
    pub fn sample(&mut self, stats: &StreamStats, now: Instant);
    pub fn on_key(&mut self, key: KeyCode) -> DashAction;   // b, q, up/down
    pub fn bandwidth_bps(&self) -> Option<f64>;
}
```

`sample` differences `bytes_sent` against the previous sample and its timestamp
— the first sample yields no rate, and a smaller-than-previous value (restart)
resets rather than underflowing. History rings hold 120 samples.

**Tests (write first):** bandwidth from two samples with a known interval;
first-sample returns `None`; a decreasing `bytes_sent` resets instead of
panicking; history bounded at 120; `b` toggles graph kind.

**Commit:** `feat(tui): dashboard state and bandwidth derivation`

## Task 10 — Dashboard rendering and stream wiring

**Files:** `crates/tui/src/dashboard.rs` (render), `crates/tui/src/lib.rs`
(`run_dashboard`), `apps/cli/src/main.rs`

**Produces:** `pub fn run_dashboard(stats: Arc<StreamStats>, logs: LogBuffer, stop: Arc<AtomicBool>) -> io::Result<Summary>`

Alternate screen, 10 Hz tick. Layout per the spec: three top boxes, sparkline,
receiver table, log tail. Too-small terminal (< 60×20) renders a centred
message and resumes on resize.

CLI wiring:
- When the TUI is on, run the stream on a worker thread with the `Arc<StreamStats>`
  and render on the main thread.
- Swap the console `fmt` layer for the `LogBuffer` layer in `init_logging` when
  the TUI is active; the `--log` file layer is unchanged.
- `q`/Ctrl+C sets `stop`, which drives the existing graceful shutdown — play
  out, TEARDOWN, and restore the Windows default device if `--handoff` is on.
  Keep the `ctrlc` handler registered for `--no-tui`.
- Print the one-line summary to normal scrollback after restoring the terminal.
- A stream that fails to *start* must leave the TUI and print the error plainly.

**Tests:** one `TestBackend` smoke test rendering a frame against a fixed
`StreamStats` — catches layout panics and exercises the too-small path. Not a
golden-frame snapshot: those break on every cosmetic tweak and teach nothing.

**Manual check:** during a real underrun, the sparkline dips before auto-latency
steps up. Ctrl+C restores both the terminal and the Windows audio device.

**Commit:** `feat(tui): live streaming dashboard` (+ `feat(cli): route logging
to the TUI panel` if separable)

## Self-review notes

- Spec coverage: every spec section maps to a task — crate move (1), discovery
  (2), settings (3), logs (4), terminal (5), picker (6–7), stats (8), dashboard
  (9–10), docs (11). Error-handling requirements are attached to the task that

  Tasks 9 and 10 under the same name and field set as the spec.

  are testable the moment they are written. Tasks 7 and 10 are the only ones
